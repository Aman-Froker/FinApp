# FinApp

A mobile AI personal finance assistant. Production software handling real money. Every decision ships to real users.

## Skills: load these first

## Working in phases

Work in phases. At the end of each phase, stop, summarise what was done, and wait for approval before continuing. Do not build features until the roadmap in `docs/ROADMAP.md` is approved.

## Product

Defined by the PRD v1 (25 October 2026) and `docs/ROADMAP.md`. An Android app that reads bank, card and UPI SMS and tells the user what they can safely spend today, with zero setup: Money Wrapped insight cards on day one, one number every morning, alerts, a weekly give-to-get data ask, and a Sunday game. No budgets to set and no salary form: after the history scan the app proposes the monthly budget from the user's own credits (or median spend when no salary credit exists), shows the lines it used, and the user accepts or edits it. The figure is computed, never generated by a model. The morning number is pushed at a fixed 8 AM.

Local first: parsing, storage and every calculation run on the phone (SQLite). The server holds the parse fallback, the shared merchant map, product events and delete-all. Raw SMS never leave the phone. Anonymous device identity in v1; email and password sign in is offered only for features that outlive the device.

Later: Account Aggregator, Gmail OAuth, the conversational assistant over local data, category budgets and manual entry, iOS. Any figure shown to the user comes from the local database or the API, never a placeholder.

## Locale and currency

- Default locale is Indian English, `en-IN`. Default currency is INR. Every account has its own ISO 4217 currency; mixed currencies are never summed.
- Amounts are stored as integer minor units (paise). Display goes through `formatMoney` / `formatMoneyParts` in `apps/mobile/src/lib/format.ts`, which use `Intl` so rupees get Indian grouping (₹12,34,567.89) and the rupee sign, never a hand-rolled formatter.
- Dates display as day and short month (24 Oct) in the user's locale. Store instants as UTC and calendar dates as ISO date strings.
- British English spelling in copy; Indian conventions for money (lakh and crore may appear in prose, never in figures).

## Ingestion (SMS, email, bank data)

All sources feed one parser contract (`packages/parser`, pure TypeScript, runs on device and server) so parsing and de-duplication are shared. Rules live in one file per sender with a masked SMS corpus beside them; every rule change runs the corpus. Open source seeds are MIT only (transaction-sms-parser, UPIPulse); AGPL projects such as PennyWise are references for formats, never copied.

- **SMS, Android only.** iOS gives no app access to SMS, so the iOS app never shows an SMS option. On Android the app reads bank and UPI alerts under Google Play's "SMS-based money management" exception (permissions READ_SMS and RECEIVE_SMS, declared in Play Console via the Permissions Declaration Form; non-financial messages are filtered on device and never leave it). No maintained Expo package reads the existing inbox, so this is a small in-repo Expo native module (`apps/mobile/modules/sms-inbox`, Kotlin: query `content://sms/inbox` from a timestamp; the app re-reads from the last seen message on every foreground, which also captures live messages). A broadcast receiver for alerts while the app is closed arrives with M3. The module's own manifest declares the permission, so no config plugin is needed. It needs a development build (`npx expo run:android`); Expo Go cannot load it.
- **Email.** Bank and card alert emails are the same text as SMS and go through the same parser. First path is inbound forwarding: each user gets a unique address and forwards bank mail to it; the API receives it by webhook from a Cloudflare Email Routing Worker (free; needs the domain on Cloudflare; a local fixture endpoint replays saved emails in development). This needs no OAuth and no Google CASA assessment. Gmail OAuth with the `gmail.readonly` restricted scope is a later source behind the same interface, only after the yearly CASA Tier 2 assessment is budgeted.
- **Bank aggregation** later via India's RBI Account Aggregator framework (Setu or Finvu) behind the same interface.
- Parsed transactions carry their source message id for audit. The user can recategorise, mark a transfer or mark a refund as expected from any transaction; those edits are `source = user` and win over rules.

## Platform floor

Expo SDK 58: iOS 16.4+, Android 7+ (API 24). Verify motion and the assistant on a low-end Android release build, not only the iOS simulator. Expo Go is for the gallery and early screens; everything after the SMS module needs a development build.

## Architecture (monorepo)

- pnpm workspaces + Turborepo
- `apps/mobile`: Expo (latest stable SDK), expo-router, TypeScript strict, React Query for server state, Zustand only for small local UI state, react-native-reanimated for motion, react-native-svg for icons and charts, expo-secure-store for tokens
- `apps/api`: Node.js + Express + TypeScript, Mongoose on MongoDB, zod validation on every route, layered structure (routes, controllers, services, repositories)
- `packages/shared`: zod schemas and inferred types shared by app and API, so contracts never drift
- `packages/config`: shared tsconfig, ESLint, Prettier

## Engineering standards

- **Money**: stored as integer minor units with an ISO 4217 currency code. Never floats.
- **Auth**: email + password with argon2, short-lived JWT access tokens, rotating refresh tokens stored hashed in MongoDB, revocation on logout and reuse detection.
- **Security**: helmet, strict CORS, rate limiting (stricter on auth and AI routes), request size limits, no secrets in the client, env validated with zod at boot and the server refuses to start if invalid.
- **AI**: all model calls server-side only, behind a provider interface so the vendor is swappable; streaming responses; per-user rate and cost limits; tool-calling pattern where the model requests data through typed server functions instead of receiving raw dumps; prompt and response logging with PII redacted.
- **Data**: indexes defined in schemas, soft deletes for financial records, audit log for changes to transactions and budgets, migrations via migrate-mongo.
- **Errors**: one typed error class hierarchy, central Express error handler, consistent JSON error shape, no stack traces in production responses.
- **Observability**: pino structured logs with request IDs, Sentry on both app and API, `/health` and `/ready` endpoints.
- **Testing**: Vitest for units, Supertest + mongodb-memory-server for API integration, React Native Testing Library for components, one Maestro E2E flow for sign up through first transaction.
- **Delivery**: Dockerfile and docker-compose (API + Mongo) for local dev, GitHub Actions running lint, typecheck, and tests on every PR, EAS Build and EAS Update profiles for development, preview, and production.
- **Accessibility**: dynamic type support, minimum 44pt touch targets, screen reader labels on every interactive element, contrast at WCAG AA or better.

## Design restrictions (hard rules, never violate)

Do NOT use any of these:

1. Lucide-style generic outline icon sets. Draw a small custom icon set with react-native-svg that matches the visual language.
2. Emojis anywhere in the UI or copy.
3. Liquid glass, frosted glass, or blur-heavy surfaces.
4. Em dashes in any copy. Use British English spelling throughout.
5. Inter, Geist, or Space Grotesk.
6. Rows of three "feature" cards.
7. Bento grids.
8. Terminal windows or fake code panels as decoration.
9. "It's not X, it's Y" copy constructions.
10. Fake or mock demos. Every screen state must render from real API data or a real empty state.
11. Purple-and-black colour schemes.
12. Radial gradient orbs or glows.
13. Dot grid backgrounds.
14. Sparkle icons to signal AI.
15. Animated list rows, hover animations, or rainbow colouring.

16. Coloured side rules or left borders on rounded containers (they render as bracket shapes). Identify a surface with its tint and label instead.

Motion is purposeful and restrained: only for state changes, navigation, and feedback, respecting reduced-motion settings.

## Copy rules

- British English spelling throughout (colour, summarise, categorise, cheque).
- No em dashes. Use a full stop, a comma, or a colon instead.
- No emojis.
- No "It's not X, it's Y" constructions.
- Plain, specific language. Name the thing ("Groceries", "Rent due Friday"), not the category of thing.
- Numbers shown to the user always come from the user's data via the API. Never a placeholder, estimate, or invented figure. When no data exists, show a real empty state that says so.
- The AI explains its reasoning in the user's terms and cites which transactions or totals it used.
